# 0006: TLS stack

Status: accepted, 2026-11-10; crypto provider graviola, owner decision
2026-11-11 (record 0021). Ticket: PGMI-829. Builds on spike A.
Checked on crates.io / docs.rs / rustsec.org, 2026-11-10: rustls 0.23.46
(2026-10-14), rustls-pki-types 1.16.0, ring 0.17.14 (2025-03-11; RustSec
lists only versions before 0.17 as unmaintained), aws-lc-rs 1.19.0,
rustls-native-certs 0.8.5 (2026-10-13), rustls-platform-verifier 0.7.1,
tokio-postgres-rustls 0.14.0 (code reused, crate not used), md-5 0.11.0,
aes 0.9.4, cbc 0.2.1, des 0.9.0.

## Context

The contract fixes six sslmodes with libpq's meaning, the default files in
`~/.postgresql/`, `sslrootcert=system` with `SSL_CERT_FILE`, client
certificates with OpenSSL's legacy encrypted keys, channel binding, direct
TLS negotiation, `require_auth`, and the TLS version in `--json`. The binary
is built static for musl and cross-built for six targets (spike D).

## Options

- **Library**: rustls (pure Rust plus ring's C and assembly; spike A passed
  with it) or native-tls/OpenSSL (a C library in every build, different
  behaviour per OS). rustls.
- **Crypto provider**: ring (cross-builds with zig, chosen by spikes A and D)
  or aws-lc-rs (rustls's default, needs CMake and a C toolchain per target,
  pulled in by default by several cloud crates). ring.
- **Verifier**: one custom verifier for all modes, or rustls's stock
  `WebPkiServerVerifier` plus `dangerous()` switches per mode. One custom
  verifier that delegates the hard parts to webpki is easier to review.
- **System roots for PostgreSQL**: rustls-native-certs (reads the OS store,
  honours `SSL_CERT_FILE`/`SSL_CERT_DIR` like OpenSSL, which is what libpq
  does) or rustls-platform-verifier (asks the OS to verify, different
  semantics per OS). rustls-native-certs.

## Decision

- One crypto provider, chosen in `tls::provider()` and installed first
  thing in `main`, so every rustls user in the process (PostgreSQL, reqwest,
  the AWS client) uses it. ring is out (PGMI-855, record 0021): the provider is
  graviola (owner, 2026-11-11), with its CPU requirement checked before any
  TLS or cloud sign-in (`tls::require_cpu`, exit 10). CI bans
  every crate that compiles C (record 0021).
- **One `PgVerifier`** with three modes: `None` (`require` without a root
  certificate; accepts any certificate but still checks the handshake
  signature), `Chain` (`verify-ca`: webpki chain verification, a
  `NotValidForName` result accepted), `Full` (`verify-full`: chain plus
  name; an IP address needs an IP SAN, which webpki checks for
  `ServerName::IpAddress`). `require` with a root certificate becomes
  `Chain`. `PGSSLCRL` is ignored.
- **Roots**: `sslrootcert`, else `~/.postgresql/root.crt` if present;
  `system` loads rustls-native-certs. PEM bundles are read with
  rustls-pki-types' PEM parser.
- **Client certificate**: `sslcert`/`sslkey`, else
  `~/.postgresql/postgresql.crt`/`.key`. Keys in PKCS#1, PKCS#8 or SEC1.
  OpenSSL's legacy encrypted PEM (`Proc-Type: 4,ENCRYPTED`) is decrypted by
  pgmi's own code, about 60 lines: `EVP_BytesToKey` with MD5 (md-5), then
  AES-128/192/256-CBC (aes, cbc) or DES-EDE3-CBC (des), the ciphers OpenSSL's
  `-traditional` output uses. A wrong password, or a result that does not
  parse as a key, is exit 10 with `decryption password incorrect`.
- **pgmi's own tokio-postgres TLS adapter**, about 150 lines adapted from
  tokio-postgres-rustls 0.14.0 (MIT), which the wire-tap spike (record
  0005) used unchanged: channel binding `tls-server-end-point` (hash chosen from the server
  certificate's signature algorithm), ALPN `postgresql` for
  `sslnegotiation=direct`, and the negotiated version for `--json`
  (`TLS 1.3`).
- Token sign-in (record 0007, 0008) refuses `disable`, `allow` and `prefer`
  before connecting, exit 10, naming the source; Google is exempt (its
  dialer supplies TLS, record 0009).
- HTTPS to cloud endpoints uses reqwest 0.13 or the AWS hyper client on the
  same ring provider. reqwest 0.13 always links rustls-platform-verifier
  (both its `rustls` and `rustls-no-provider` features enable it), so HTTPS
  trust comes from the OS verifier; this is also what forces native macOS
  builds (record 0018).

## Consequences

- The provider is one line, the documented fallback if graviola goes stale;
  both pure-Rust candidates pass the same TLS cases (record 0021).
- Encrypted PKCS#8 keys (`ENCRYPTED PRIVATE KEY`), which Go refuses, are
  added through the `pkcs8` crate: libpq reads them, so a key that works with
  psql works with pgmi.
- As built (PGMI-833, `conn/keys.rs`): legacy PEM with AES-128/192/256-CBC
  and DES-EDE3-CBC, and PKCS#8 under PBES2 (PBKDF2 with SHA-1 or SHA-256,
  scrypt; AES-CBC or DES-EDE3-CBC), checked by hand against `openssl rsa
  -traditional`, `openssl ec` and `openssl pkcs8 -topk8` output, and PKCS#8
  under PKCS#12 PBE (`-v1 PBE-SHA1-3DES`, OID 1.2.840.113549.1.12.1.3): the
  RFC 7292 appendix B key derivation with SHA-1 from the `pkcs12` crate
  (already in the tree through `p12-keystore`, pure Rust), then
  DES-EDE3-CBC. Other PKCS#12 PBE variants (RC2, RC4, two-key 3DES) stay
  exit 10 naming the file. Case `tls/encrypted-pkcs8-client-key`; a unit
  test opens an OpenSSL-written key.
  A missing password is exit 10 asking for `sslpassword`/`PGSSLPASSWORD`; the
  key password is redacted like the connection password.

## Serves

TLS; Cloud sign-in; Timeout, cancellation, interruption (cancel over TLS and
direct TLS); Encrypted legacy client keys and require_auth are kept;
sslmode=allow retries with TLS.
