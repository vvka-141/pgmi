Programmable PostgreSQL deployments

pgmi

Your deploy.sql applies changes, can run database tests before COMMIT, and aborts the deployment if a test fails. pgmi loads your project into one PostgreSQL session; your SQL decides what runs and when it commits.

See a complete deployment Coming from Flyway or Sqitch?

Execution model

pgmi prepares the session. Your SQL decides the deployment.

Load

Project files, metadata, tests, and parameters become session-scoped temporary tables and stable views.

Decide

deploy.sql queries those views and executes what it selects, choosing ordering, filtering, transactions and idempotency. PostgreSQL reports notices and errors directly.

Test

CALL pgmi_test() runs your __test__/ tree against the uncommitted changes. A directory's fixture applies to every test below it, and each test rolls back to its directory's fixture state. A failing test aborts the transaction it runs in.

Start here

Three ways to start a project.

Minimal — the default

Two files: a deploy.sql loop that runs every SQL file in path order, and hello_world.sql. No test gate supplied: add CALL pgmi_test() to your deploy.sql when you want one.

What each template writes

The basic template

Tables in physical/ run once, tracked in a ledger that rejects changes to files already applied; views and functions in semantic/ re-run on every deploy; tests run before the commit. PostgreSQL 15+.

See a failing test abort the deployment

The advanced template

Your application's backend in PostgreSQL, as code you own: HTTP API, sign-in, tenancy and audit, served by reference gateways in five languages. Tests run before the commit. PostgreSQL 18+.

Read the guide before choosing it

The basic and advanced templates also write an AGENTS.md and skills, so a coding agent learns the project's conventions before it edits. pgmi takes no position on architecture: each template is a starting point you own (what pgmi gives you, and what you own).

Where it fits

Deployment behavior written in SQL.

Use pgmi when deployment logic belongs close to the database: environment-aware changes, test gates, data loads, generated APIs, or application behavior expressed in SQL.

  • CLI flags stay focused on infrastructure: connections, parameters, compatibility, observability.
  • Deployment behavior stays in deploy.sql, where it can be reviewed and tested with the rest of the database code.
  • Coding agents get the binary's session API from pgmi ai contract and drive pgmi over MCP with pgmi serve. MCP endpoints your own application serves at runtime are a separate thing, written in the advanced template.
